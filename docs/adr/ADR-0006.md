# ADR 0006: Translation Abstraction with Argos Translate as First Engine

Date: 2026-07-31

## Status

Approved

## Context

Live translation of the source transcript is a core product feature, not an afterthought: a user may be watching speech in one language and want captions in another (e.g., Japanese speech → English captions). Requirements:

- Translation must work locally/offline in the MVP — transcripts must not leave the machine.
- The user selects a source language (or auto-detect) and a target language; when no direct language pair model is installed, the engine should be able to pivot through an intermediate language.
- The rest of the C# application must remain independent of any single translation provider.

The user selected **Argos Translate** as the first engine. Argos is a genuine local/offline translation engine with installable language models, supports pivoting through an intermediate language, and runs on CPU or CUDA. Its caveat is that it is **Python-based**, while our application is C#/.NET 8 + WPF.

## Decision

Define `ITranslationEngine` in `UniversalCaptions.Core` (namespace `UniversalCaptions.Core.Translation`) as an engine-neutral interface, mirroring the `ISpeechToTextEngine` refinement in ADR-0003: domain contracts live in the pure contract layer so downstream packages (`UniversalCaptions.Captions`) depend only on Core, never on an implementation project. `UniversalCaptions.Translation` owns only the concrete `ArgosTranslationEngine` adapter.

```text
Source Transcript
        ↓
ITranslationEngine
        ↓
Translated Transcript
```

Concrete engines implement it:

- `ArgosTranslationEngine` (Argos Translate) — first engine
- Cloud engines are interface-compatible but **not enabled in the MVP** (require explicit opt-in and disclosure)

Because Argos is Python-based, it is **never embedded in the .NET process**. `ArgosTranslationEngine` launches and manages a local Argos process (subprocess or local service) and communicates over a simple line protocol:

```text
WPF / .NET 8
      │
      │ ITranslationEngine
      ↓
ArgosTranslationEngine
      │
      ↓
Local Argos process
      │
      ↓
Argos language model
```

Argos model/pair selection and the process-protocol details are deferred until a latency/quality benchmark on target hardware (Slice 3/6), following the same pattern as the Whisper model-size decision (ADR-0003).

### Slice 3 Resolution (2026-08-01)

Verified on the dev machine with Argos Translate 1.11.0 (Python 3.11 venv under `artifacts/argos/`, git-ignored):

- **Process protocol:** newline-delimited JSON over stdin/stdout (`argos_translate_server.py`, bundled in `UniversalCaptions.Translation/Server/`). The engine (`ArgosTranslationEngine`) spawns `python -u <script>` and serializes requests through a gate; startup is confirmed with a `ping`; errors map to `TranslationErrorKind`; the process is killed on timeout/dispose. C# has no Python dependency; Python is a deployment prerequisite.
- **Language pairs (all available as direct packages from the Argos index):** `en→tl`, `tl→en`, `ja→en`, `en→ja`. Pivoting (`CompositeTranslation`, through the intermediate whose code is reported as `pivotLanguage`) works for pairs without a direct model (verified `ja→tl` via `en`).
- **Known limitation:** Argos sentence-boundary detection (`StanzaSentencizer`) does not support `tl` as a **source** language (verified `ValueError`). The MVP pairs use `tl` only as a **target**, so this does not block Slice 3; `tl→*` requires a pivot-capable source or an upstream fix.
- **Benchmark evidence:** `docs/reports/BENCHMARK_REPORT.md` (Slice 3 section) — model load ~12–14 s on first request (en→tl), steady-state latency 56–1050 ms/pair, Argos child process working set 468–864 MB as models load, finals-stream throughput 70–220 ms/segment, identical-input caching makes repeated finals effectively free.
- **Contract location refinement:** `ITranslationEngine`, `TranslationResult`, and `TranslationException`/`TranslationErrorKind` live in `UniversalCaptions.Core.Translation` (namespace `UniversalCaptions.Core.Translation`), so `UniversalCaptions.Captions` (Slice 4) depends only on Core. `UniversalCaptions.Translation` owns `ArgosTranslationEngine` and its process seam. Auto source-language detection is **not** available in Argos 1.11 (`detect_language` absent); the MVP takes the source language from user selection.
- The open question (pair/process-protocol selection) is now resolved: process protocol as above; default pairs `en→tl`, `ja→en`, `en→ja` (direct); pivoting available for other pairs.

## Consequences

- The pipeline (capture → STT → captions) never depends on a specific translation vendor.
- A fake translation engine gives deterministic tests for the caption service without Python or language models.
- Transcripts stay on the machine in the MVP, satisfying the privacy model.
- The C# application has no Python dependency; a Python runtime is a deployment prerequisite for the local Argos process.
- Cloud translation, if added later, requires explicit configuration and on-screen disclosure that transcripts leave the machine.
- Argos startup cost, model downloads, and per-pair pivoting behavior are benchmark decisions, not upfront commitments.

## Alternatives Considered

- **Cloud translation (e.g., Azure Translator)**: best quality and breadth, but sends transcripts off-machine and requires keys/account; conflicts with the local-first MVP privacy model. Rejected for MVP.
- **Small local LLM via ONNX (e.g., Phi-3)**: higher quality/flexibility but several GB of model and slower CPU inference for an overlay app. Rejected for MVP.
- **Raw Marian NMT integration**: excellent C++ NMT framework, but considerably more model/runtime integration work than Argos with no MVP benefit. Rejected.
- **Embedding Python directly into the .NET process**: fragile runtime coupling and packaging; rejected in favor of isolating Argos behind a local process.
- **Tightly coupling to Argos**: rejected — the `ITranslationEngine` abstraction is required to keep translation options open.
