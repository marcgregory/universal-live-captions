# ADR 0007: Boundary-Aware Streaming Transcript Commit

Date: 2026-08-03

## Status

Proposed

## Context

The live caption overlay is stable: it shows only committed FINAL captions (never the churning active line), keeps a Tagalog-only display while a real-time translation is pending, and preserves captions across Stop via a bounded drain. Those layers are proven. The remaining quality defect is **how finals are carved out of the audio**, which produces fragmented, bitin captions like:

```text
"At gusto ko"
"At ginagamit ko"
"Kaya"
"artipisyal na katalinuhan"
```

Root cause has been traced to the streaming commit path, not to display, translation, or wrapping. The caption service (`CaptionService.ProcessFinal`) only deduplicates (exact / leading-subset / extension-overlap) and never creates boundaries. The boundaries are drawn by `StreamingTranscriptCommitter.Update`, which commits on **prefix stability alone**:

```text
Whisper decode #1   →  "At gusto ko"
Whisper decode #2   →  "At gusto ko paunahin iyan"
CommonPrefix        →  "At gusto ko"
StabilityWindow = 2 →  FINAL "At gusto ko"
```

So today "final" means *this text has been identical across two consecutive decodes* — **not** *this thought/sentence has completed*. Concretely:

- `StabilityWindow=2` is the minimum that can observe byte-identity at all; it gates on "has changed for ~1 decode interval," not on a completed utterance.
- `StreamingTranscriptCommitter.ConcatSegments` flattens the decoded `TranscriptSegment` list (which carries `Text`, `Start`, `End`) into a single string, discarding structural/utterance boundaries. Those boundaries are then used only for position estimation (`AdvanceCommittedUntil`), never for the commit decision.
- Whisper itself already proposes boundary at segment/silence level, so a meaningful boundary source exists but is currently unused.

A secondary defect — the **duplicate/repeated semantic content** (e.g. "artipisyal na katalinuhan" appearing twice; a full sentence re-appearing) — is hypothesized to live in the **trim/overlap + `CommittedUntilUtc` estimation** interaction, not in the commit rule itself. `CommittedUntilUtc` is interpolated from segment positions, and when it drifts, `TrimToCommitted` slices a repeated tail that the whole-word overlap stripper then fails to recognize (short overlaps back off and are kept), re-emitting text already committed.

Both concerns must be separated and addressed in a specific order: boundary-aware commit needs the trim/`CommittedUntilUtc` correctness fixed first, as a hard prerequisite.

## Prerequisite: trim-boundary correctness (`CommittedUntilUtc`) — MUST come first

Before attaching a boundary-aware commit rule, the estimate of `CommittedUntilUtc` must be correct and anchored to a real recorded boundary, not an interpolated off-the-air fraction. The causal chain we must avoid is:

```text
wrong commit boundary
   ↓
wrong CommittedUntilUtc
   ↓
wrong audio trim
   ↓
tail re-appears
   ↓
duplicate FINAL
```

Because a boundary-aware commit will drive more, earlier commits through this same machinery, shipping it before the estimation is correct risks amplifying the duplicate defect. Therefore **correct trim-boundary estimation is a prerequisite** to any commit rule change, and its acceptance criteria are:

- `CommittedUntilUtc` advances only to a point that is **both** committed **and** meaningful (e.g. the `End` of a committed segment), not to an arbitrary interpolated character offset inside a segment.
- The trim removes audio only up to such a committed boundary; the tail that was committed is never re-fed as fresh audio.
- Duplicate-capable behavior is verified before and after the boundary change so improvements are attributable.

## Evidence note: `CommittedUntilUtc` confirmed as a prerequisite issue (2026-08-03)

Code-level trace (`StreamingTranscriptCommitter.AdvanceCommittedUntil`, `CommitStableText`, `StreamingTranscriptCommitter.FindTailOverlap`; `WhisperSpeechToTextEngine.TrimToCommitted`) confirms the defect. This is a **confirmed prerequisite issue**, not yet a proposed implementation change.

### How `CommittedUntilUtc` is derived

`AdvanceCommittedUntil` maps the last committed character position onto the decode window's segment positions:

- **Case A** — the committed length covers a whole segment (`_currentEpochCommittedLength >= segmentEnd`): snap to the **real segment `End` boundary**. ✅
- **Case B** — the committed length falls *inside* a segment (`> segmentStart`): a **uniform-linear interpolation** of the character offset across the segment's `Start`→`End` time span produces a **timestamp inside the segment/word**. ⚠️ Real speech is not uniform, so this interior position does not correspond to the true acoustic end of the committed text.
- **Case C** — committed length is at or before the segment start: **no advancement**.

Only Case A yields a true Whisper boundary; Case B is the defect. The mapping also re-anchors to `_lastWindowStartUtc + segment.Start/End` of the *current* decode each epoch, so the interior estimate shifts as the window slides.

### The defect chain

```text
committed char position
        ↓
Case B interpolation
        ↓
interior timestamp
        ↓
TrimToCommitted
        ↓
possible tail re-decode
        ↓
FindTailOverlap may miss short overlap
        ↓
duplicate FINAL
```

- `TrimToCommitted` cuts audio whose `chunkEnd ≤ CommittedUntilUtc` (capped by `windowEnd − CommitOverlap`); an interior `CommittedUntilUtc` approximation removes an arbitrary fraction of the tail.
- When that leaves already-committed tail audio in the buffer, the next epoch re-decodes it; `FindTailOverlap` strips a *whole-word* overlap (≥ 4-char) that it can reliably recognise, but **short/repeated tails (e.g. "Kaya", a 1–2-word boundary overlap) back off and are kept**, so the tail is re-emitted as a fresh FINAL → duplicate.

### Fix direction: boundary snapping — but snap direction is **undecided**

"Snap `CommittedUntilUtc` to a real boundary" is the candidate fix; it alone does **not** prove *which* boundary is correct. Backward vs forward snap change the trim/committed invariants differently:

```text
Backward snap                          Forward snap
commit:  |---------X                   commit:  |---------X
segment: |-----------|                 segment: |-----------|
boundary: |------B----|                 boundary: |-----------B
             ↑ trim here                               ↑ trim here
```

- **Backward snap** (to the end of the segment that finishes *before* the cut): retains a small already-committed audio fringe and relies on the overlap handler to absorb it. Safer against losing uncommitted content, but must lean on `FindTailOverlap`.
- **Forward snap** (to the end of the segment that *contains* the cut): trims more aggressively, but can discard audio that belongs to text **not yet committed**, truncating the tail/partial.

Neither direction is declared correct here: the choice must be validated against the commit/trim invariants (and the duplicate/truncation acceptance criteria above) before implementation, to avoid introducing a new duplication or truncation bug. **Boundary snapping is the candidate fix; snap direction remains undecided pending validation.**

### Snap-direction decision (2026-08-03): **Backward snap**

**Chosen:** `CommittedUntilUtc` snaps to the **last fully committed Whisper segment.End**. No code is changed here — this is a design decision, **not** an approval to implement.

Decision criteria — I1 outranks I2 because trimming audio is irreversible (missing words forever), while re-emission is recoverable (can drop the dup):

- **I-1 (priority)**: never permanently discard audio that contains text **not yet committed**.
- **I-2**: already-committed text must not be re-emitted as new finals.

Evaluation that drove the choice:

- **Backward snap** — trims at the last *fully committed* segment's `End`, so the current segment — including any not-yet-committed suffix — stays in the buffer. **I-1 preserved by construction.** It keeps an already-committed fringe (roughly one in-progress segment, inside the `CommitOverlap=1.5 s` zone). Short (<4-word) overlaps of that fringe may still re-emit → a **separate I-2 concern**, not a trim-safety violation.
- **Forward snap** — trims at the current segment's `End`, crossing the commit cut into the **uncommitted suffix** of that segment and **permanently discarding it** (irreversible audio loss). `CommitOverlap` only retains the most-recent 1.5 s and does not protect an older suffix. **Rejected.**

### Scope held deliberately tight

> Backward snap **fixes the trim-safety invariant (I-1); it does not claim to have fixed fragmentation or the short-tail duplicates (I-2) yet.**

- **I-2 stays a separate follow-up:** short retained tails (1–3 words) can still duplicate because `FindTailOverlap` rejects `<4`-character overlaps.
- **Do not modify `FindTailOverlap` in this step.** Short-tail overlap handling is a separate design/validation step, not bundled here.

### Validation evidence — backward-snap invariants (2026-08-03)

Step-by-step validation of the **proposed** backward-snap semantics against the **current** `TrimToCommitted` buffer/trim mechanics. Design only; no code changed.

**I-1 — No data loss: PASS.** Simulated the three commit landing points:

```text
commit exactly at a segment end        → snap = that segment's End       (fully committed)
commit inside a segment               → snap = previous segment's End   (suffix retained)
commit at/before a segment start     → snap = previous committed End    (next segment retained)
```

- Backward snap always points at a **fully committed `segment.End`**. Because segment `End`s are monotonic with text order, any audio at/before that point is fully committed.
- `TrimToCommitted` keeps the uncommitted suffix: it stops while `chunkEndUtc <= trimUntil`, so chunks ending past the boundary are retained.
- **Chunk-straddling** further protects the cut: a chunk that starts before the boundary but ends after it (`chunkEndUtc > trimUntil`) is kept (the loop breaks), so audio is never sliced through the boundary.
- **Result:** backward snap guarantees I-1 under the current buffer/trim mechanics.

**I-2 — duplicates are an overlap-handling concern, not a trim-safety failure.** After the snap, the retained audio that is re-decoded is the committed *fringe* of the current segment:

- **≥ 4 chars, whole-word aligned** → existing `FindTailOverlap` recognises and strips it (no duplicate).
- **< 4 chars** → the existing `if (end < 4) continue` guard **intentionally lets it through** → re-emits as a new final (duplicate).

So any remaining duplicate is the **documented `<4`-character `FindTailOverlap` guard**, by design — not a trim-safety violation.

**Gate:** this evidence **clears the prerequisite gate** for designing the boundary-aware FINAL rule. It does **not** validate that rule itself.

**Preserved:** no `FindTailOverlap` change; no boundary-aware FINAL implementation; wrapping, display, Argos, and Stop-drain remain untouched.

## Decision

Change the streaming commit from a stability-only rule to a **boundary-aware rule with a hard latency fallback**:

```text
stable prefix
    │
    ├── meaningful boundary appears ──→ FINAL
    │
    └── boundary does not appear
            │
            └── hard latency cap reached ──→ current word-boundary fallback (FINAL)
```

Formally, we replace:

```text
stable(current complete-prefix)                          → FINAL
```

with

```text
stable(current prefix) AND meaningful boundary           → FINAL (expected)
else if hard latency cap reached on the stable prefix    → FINAL (bounded fallback)
```

Requirements on the new rule:

- **Never wait indefinitely.** There is always a hard cap that falls back to the current behavior. The invariant is explicit: a caption must be released no later than the point at which it would have been released today (bounded fallback), so this change is strictly liability-preserving with respect to *latency* **only once the fallback budget is precisely defined** — it is **not** automatically assumed to be no-slower than today until that budget is specified and validated. Stating "cannot be worse than current latency" without defining the budget is a non-goal.
- **Reuse existing data.** The boundary signal comes from the already-captured `TranscriptSegment` `Text/Start/End` we already hold; no new model or network calls.
- **Both-and, not either-or.** A boundary alone is not enough (Whisper can close a segment mid-thought under noise); the stable prefix requirement remains.
- **Latency budget is its own design artifact** with: (1) a hard cap (e.g. commit a stable prefix no later than some seconds / some number of committed segments), (2) a tail/idle rule so a genuine mid-utterance pause still stabilizes, and (3) defined interaction with `DecodeInterval`/`StabilityWindow`.

### Boundary sources, in priority order

1. **Whisper segment boundary** — the strongest "thought finished" signal we already get.
2. **Meaningful inter-segment silence / word gap** — the gap between consecutive segments (end→start) as a secondary signal.
3. **Hard latency fallback** — the cap above, committing at the current word boundary when no meaningful boundary has appeared in time.

### Algorithm design — boundary-aware FINAL (2026-08-03, design only, no code)

The precise eligibility state machine. Replaces the current `stable → commit` with a gated rule operating on the **existing `stable` string and the real `TranscriptSegment` list** — never on an estimated/interpolated timestamp.

```text
update(stable, partial, segments, now):

    if stable non-empty AND stableEndsAtSegmentBoundary(stable, segments):
        → FINAL                       (clean case 1)
    elif stable non-empty AND boundaryBudgetExpired(stable):
        → FINAL                       (fallback, commits current word-backed stable)
    else:
        → remain uncommitted; continue partial per current rule

    stableEndsAtSegmentBoundary(stable, segments):
        segment = segmentContaining(lastStableChar, segments)   # via cumulative char spans
        return stable.length == segment.cumulativeEnd            # ends exactly at segment end
```

**The four cases, pinned:**

1. **Stable prefix ends exactly at a segment boundary** → eligible immediately. The preferred case; structurally true, no estimated timestamp.
2. **Stable prefix ends inside a segment** → do **not** FINAL merely because stable. Keep waiting for the next boundary (stops `At gusto ko`).
3. **A boundary appears but stable does not reach it** → do **not** commit the boundary's text. Stability remains mandatory; only the common-across-2-decodes portion counts, never the whole segment.
4. **No meaningful boundary arrives** → the hard latency cap permits a bounded fallback FINAL (commits exactly today's word-backed stable). Prevents indefinite hold.

**Operate on segment structure, not character interpolation.** The boundary test compares stable's length against cumulative per-segment char extents — the same cumulative mapping `AdvanceCommittedUntil` already builds — and asks only "does stable end at a segment boundary?". Design note: that cumulative tracking should be extracted into a small reusable segment-index (rather than living inside the trim/time estimator) before implementation.

**Hard-cap fallback basis (settled): time since the stable prefix first became stable** (`StableSinceUtc`), not since decode and not since first-eligible. This directly bounds the *additional* waiting introduced by the boundary gate, which is the responsiveness property we must control.

Invariant:

> A stable prefix may wait for a meaningful boundary, but never longer than `BoundaryWaitBudget` after it first became stable.

- `StableSinceUtc` = decode-pass timestamp when the current stable prefix length was first confirmed stable (2 consecutive passes for `StabilityWindow=2`). Reset when `stable` grows or the stable text changes. When `now − StableSinceUtc ≥ BoundaryWaitBudget` → fallback commit.
- **Fallback commits exactly the current word-backed stable prefix** — same output as today's `CommitStableText`. It does **not** reach into the uncommitted/revising tail (that stays partial) and does **not** conflict with `CommittedUntilUtc` (the fallback boundary is still backward-snapped to a fully-committed segment end, preserving I-1).

**`BoundaryWaitBudget` sizing — PRELIMINARY, not yet an accepted invariant.** Defined precisely:

> Maximum additional time a stable prefix waits for a meaningful boundary before today's word-backed fallback is allowed.

Derived from the existing timing model, **not** plucked as a "few seconds":

- `DecodeInterval ≈ 1 s`, `StabilityWindow = 2` → current stable-prefix detection already costs ~**one additional decode interval** after the prefix first appears.
- The boundary gate adds waiting **after stability**. `BoundaryWaitBudget` bounds that extra wait only.

Candidate table (kept provisional, not locked):

| Budget                       | Effect                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| **1 × interval (~1 s)**      | Very responsive, but may fall back before Whisper yields another useful boundary                        |
| **2 × interval (~2 s)**      | Reasonable starting candidate; ≈ 2 decode opportunities                                                 |
| **3 × interval (~3 s)**      | Better boundary quality, but noticeably higher tail latency                                             |
| **Adaptive**                 | Potentially best, but more complexity and harder to validate                                            |

**Current choice: `2 × DecodeInterval ≈ 2 s` — provisional candidate only, NOT accepted.** 2 s is kept because it affords ~2 decode opportunities (matching the stability window cadence), but it is unvalidated against real latency behavior and must be re-derived from the Slice 6 / SAPI E2E measurements before it can be promoted. Replacing `StabilityWindow=2` with another unmeasured constant is explicitly a non-goal.

**Design caveat to settle before implementation (recorded, not fixed):** `Update` clears `_recentTexts` and resets `_currentEpochCommittedLength = 0` whenever `windowStartUtc` changes. That would also discard an in-progress `StableSinceUtc` mid-wait. The boundary design must carry wait state **across epoch resets** (or recompute `StableSinceUtc` from the persistent `_committedText`/segment time) so the cap can be measured stably.

### Acceptance criteria for uptake (must hold before implementation is considered complete)

Before any boundary-aware commit code is written, the design's semantics must be verifiable against all of the following; none may be a "we trust it" assumption:

1. **`At gusto ko` must NOT finalize** merely because it was stable — being stable without a meaningful boundary is insufficient to FINAL.
2. **Boundary within the budget wins.** If the next Whisper boundary arrives within `BoundaryWaitBudget`, the commit uses that boundary (case 1), not a premature fallback.
3. **No boundary → bounded fallback.** If no boundary arrives, the fallback fires at the budget, never later (no indefinite wait).
4. **Fallback adds no more than the budget** — measured added latency from `StableSinceUtc` to fallback ≤ `BoundaryWaitBudget`.
5. **Epoch resets preserve the pending stable-prefix wait state** — `StableSinceUtc` survives `windowStartUtc` changes (the caveat above must be resolved this way).
6. **`CommittedUntilUtc` stays backward-snapped to a real segment boundary** (I-1 preserved; no revert to interpolated timestamps).
7. **Rapid speech causes neither missing text nor repeated FINALs** — every committed word appears exactly once, with no gaps.

### Implementation design (2026-08-03, design only, no code)

Change is made **inside `StreamingTranscriptCommitter` only**, keeping the public `Update(...) → CommitResult` contract intact.

**Current conceptual flow** (for contrast):

```text
Update(segments) → concat text → CommonPrefix(recent decodes) → CommitStableText() → FINAL
```

**Proposed flow:**

```text
Update(segments)
   ↓
retain segment structure
   ↓
calculate stable prefix
   ↓
map stable-prefix end → segment index / cumulative char span
   ↓
       ┌── exact meaningful boundary?
       │       ↓
       │     FINAL
       │
       └── no boundary
               ↓
        StableSinceUtc + budget?
            no         yes
            ↓          ↓
         wait    word-backed fallback
```

**9 design rules:**

1. **Preserve the segment list.** `ConcatSegments()` must not become the *only* representation. Both `stableText` and `segments[]` are kept: the concatenated string serves `CommonPrefix`; the segments serve the structural boundary query.
2. **Stable-prefix span via cumulative char spans.** Compute boundary by character extents (segment 0 `[0..18]`, segment 1 `[18..37]`, ...). `stable.length == 37` → lands exactly on segment 1's end → meaningful boundary. `stable.length == 29` → inside segment 1 → not yet eligible. **No timestamp interpolation participates.**
3. **Track `StableSinceUtc`.** Set when the stable prefix first appears; subsequent decodes retaining the *same* stable prefix must not reset it. A grown prefix is a new stable state and its timer resets per the precise lifecycle rule (see open item below).
4. **Boundary wins.** If `stable`'s end coincides exactly with a Whisper segment boundary, commit immediately. The budget is not consulted.
5. **No boundary → wait.** If `stable` ends inside a segment, do not emit FINAL; keep it stable internally until a boundary or the budget.
6. **Budget expiry → existing fallback.** When `UtcNow − StableSinceUtc ≥ BoundaryWaitBudget`, commit **exactly the word-backed stable text the current implementation would have committed**. The fallback changes *when* we commit, not *what* text we commit — minimizing behavioral risk.
7. **Epoch reset must preserve pending state.** If the window rolls while `stable = X`, boundary not reached and timer running, that pending state must survive the `_recentTexts` / `_currentEpochCommittedLength` reset. The pending prefix survives; the *segment mapping* is recalculated against the new window. Conceptually: Epoch N (pending) → window rolls → Epoch N+1 (pending survives, new segments evaluated) → boundary OR budget → commit.
8. **Keep `CommittedUntilUtc` separate.** The boundary-aware commit logic does **not** invent a new `CommittedUntilUtc`. After a FINAL is actually committed, the committed structural boundary is backward-snapped to a real segment end → `CommittedUntilUtc` (I-1 preserved).
9. **Keep the change atomic.** The implementation must **not** simultaneously modify `FindTailOverlap`, `CaptionService`, Argos, overlay rendering, wrapping, `StabilityWindow`, `DecodeInterval`, or stop/drain behavior. This isolates the experiment: **does boundary-aware committing eliminate premature FINAL fragmentation without introducing truncation or additional duplicates?**

**Open item before coding — pin the `StableSinceUtc` lifecycle — RESOLVED below.** The unambiguous rule for *what constitutes the same stable prefix* across successive decodes and epoch resets — especially when stable text **grows** — was the last unspecified part. It is now defined by the **`StableSinceUtc` state-transition table** and its **extension / regression / replacement** classification. Without it, `StableSinceUtc` could erroneously reset every time the prefix extends, defeating the cap.

### `StableSinceUtc` state-transition table (2026-08-03, design only, resolved)

**Central rule (binds the invariant):**

> The timer measures how long the stable prefix has remained **continuously stable**, not how long the latest/longest string has existed. **Growing the stable prefix must not reset the timer.**

Rationale: if growth reset the timer, a continuously evolving stable prefix (every decode adds text) could keep restarting and wait indefinitely — defeating the whole cap. Instead the timer runs from first convergence and the fallback commits the *current (fullest)* stable at expiry, so the committed caption is complete, not an early fragment.

**Canonical `StableSince` lifecycle table:**

| Transition                                    | Stable text                               | Timer                     |
| --------------------------------------------- | ----------------------------------------- | ------------------------- |
| `""` → stable                                | `"" → "At gusto ko"`                      | **Start** (`now`)         |
| stable unchanged                             | `"At gusto ko" → "At gusto ko"`          | **Continue** |
| stable grows (extension)                     | `"At gusto ko" → "At gusto ko paunahin"`  | **Continue, do NOT reset** |
| stable regresses (retraction)                | `"At gusto ko paunahin" → "At gusto ko"`  | **Continue** (core unchanged) |
| stable replaced (unrelated text)             | `"At gusto ko" → "Kumain ako"`            | **Reset** (new interval) |
| epoch rolls, stable content preserved      | same pending stable content               | **Continue** |
| epoch rolls, stable content diverged      | replaced                                 | **Reset** |
| boundary becomes available                   | stable + boundary                        | **Commit → clear/continue idle** |
| budget expires                               | stable, no boundary                       | **Fallback commit → clear** |
| no stable text                               | `"" → ""`                                 | **No timer** |

**Extension vs regression vs replacement — must not treat all text changes alike.** Define these over consecutive stable values `old` → `new` via ordinary prefix comparison:

- **Unchanged:** `new == old` → continue.
- **Extension:** `new.StartsWith(old)` (`old` is a strict prefix) → **continue** (timer untouched). This is the growth case; must not reset.
- **Regression/retraction:** `old.StartsWith(new)` (`new` is a strict prefix of `old`) → **continue**. The surviving prefix was continuously stable throughout, so the total wait is preserved; retracted tail is simply no longer committed.
- **Replacement (unrelated):** neither is a prefix of the other (they diverge within the old extent) → **start a new interval** (`StableSince = now`). This is genuinely different text, so a fresh wait begins.

Because in-code `stable` is derived as `CommonPrefix(_recentTexts)`, within an epoch it can only hold or extend (append-only audio + longer overlap re-decoded windows) — replacement with an epoch occurs only at an **epoch roll** or when a new (noisy) decode revises earlier content. Capturing it as the prefix relations above covers every in-code transition.

**Clock requirement for determinism:** the committer currently is clock-free (`StreamingTranscriptCommitter` uses only `windowStartUtc`). Computing `now − StableSince` needs wall-clock, so introduce an injectable clock (`Func<UtcNow>`) — the same pattern already used by `CaptionService`. This keeps tests deterministic (no sleeping) and is part of implementation, not the STT engine contract change.

**Budget-expiry fallback behavior:** when `now − StableSince ≥ BoundaryWaitBudget`, commit **the current full word-backed stable prefix** (whatever `stable` is now, passed through `CommitStableText`) — i.e., the fallback changes *when* we commit, not *what* text we commit, matching the "both-and" rule. So an early-fragment concern (`At gusto ko`) is avoided: if no boundary arrives within the budget, whatever the speaker has produced by then is committed whole, not the first fragment.

**Guarantee this table provides:** worst-case extra wait from the first stable convergence to fallback ≤ `BoundaryWaitBudget`, regardless of how transcription noise changes ordering; growth never extends the wait, and regression/replacement handle revisions without scaling the bound.

### Implementation plan (2026-08-03, design only, no code)

Deliberately narrow; each rule maps to a concrete code/test location inside `StreamingTranscriptCommitter`. **Do not change `StabilityWindow` or `DecodeInterval`.**

**1. Committer state — add only what the new lifecycle requires:**
- pending stable-prefix state (the stable extent being held for a boundary);
- `StableSinceUtc`;
- injectable `UtcNow` (`Func<DateTime>`);
- any epoch-independent representation needed to preserve the pending stable state across window rolls.
Everything else stays as-is.

**2. Preserve structural segments during `Update()`.** Keep both representations:
```
segments → concatenated stable text   (existing `ConcatSegments` → `CommonPrefix`)  = decides stability
         → segment spans              (new: per-`TranscriptSegment` char extents)    = decides boundary eligibility
```
`CommonPrefix` still decides **stability**; the spans decide **boundary eligibility**. `ConcatSegments` must not become the only view.

**3. Stable-prefix classification.** On every update classify the new stable prefix as one of `empty | unchanged | extension | regression | replacement`, then apply the ADR rules (unchanged/extension/regression → timer continues; replacement → timer resets; empty → no timer).

**[Invariant] Growing stable text never resets `StableSinceUtc`.**

**4. Boundary eligibility.** After stability is established: map the stable prefix's character end into the segment spans; ask only *does it terminate exactly at a meaningful segment boundary?* → yes: **COMMIT**; terminates inside a segment → **WAIT**. No timestamp interpolation answers this.

**5. `BoundaryWaitBudget`.** Fallback condition is `UtcNow − StableSinceUtc ≥ BoundaryWaitBudget`. If no boundary by then, commit the **current word-backed stable text** (not an earlier fragment), then clear the pending stability state.

**6. Epoch rollover.** When the window rolls: pending stable state survives; the structural segment mapping is rebuilt from the new epoch. The implementation must **not** restart the timer merely because `_recentTexts`/`_currentEpochCommittedLength` was reset.

**7. `CommittedUntilUtc` stays backward-snapped.** FINAL commit → last fully-committed segment `.End` → `CommittedUntilUtc`. No Case-B interpolation. **Do not modify `FindTailOverlap` in this change.**

### Unit-test plan (all must pass before live testing)

**Stability lifecycle — each invariant independently:**
- first stable prefix starts the timer
- unchanged prefix preserves the timer
- extension preserves the timer
- regression preserves the timer
- replacement resets the timer
- empty clears / does not start a timer
- epoch rollover preserves the timer

**Boundary behavior:**
- stable prefix ending exactly at a segment boundary → FINAL
- stable prefix inside a segment → no FINAL
- boundary without stability → no FINAL
- boundary becomes available later → FINAL
- no boundary + budget expires → fallback FINAL

**Latency:**
- fallback occurs no later than `BoundaryWaitBudget`
- growing stable text cannot indefinitely extend the deadline

**Trim safety:**
- backward snap remains at a fully committed segment end
- the uncommitted suffix remains available

**Regression protection:**
- existing stable-prefix behavior remains intact where the new gate does not intervene
- no changes to overlay / wrapping / Argos / Stop behavior

**Implementation gate.** All tests above must pass **before** the live video test. The live test targets the already-observed failures: `"At gusto ko"` / `"Kaya"` fragmentation — the caption should wait for a meaningful boundary when one arrives, and still produce a bounded fallback when it does not. Judge **fragmentation, duplicates, missing words, and latency separately**. This isolates the change so any breakage is attributable to the committer, not the already-stable display/translation layer.

### Fallback rule refinement (2026-08-04): **Boundary-preserving fallback (Option B)** — locks in what the fallback may commit

The provisional fallback above ("commit today's word-backed stable prefix at the cap") was validated live with a temporary per-FINAL tracer against a real APP + ggml-base run of `jfk_long.wav` and proved to be the **source of the premature fragments**: every bad FINAL was committed with `boundary_found: false, fallback_used: true` (Case 2) — the cap force-committed interior stable text like `" And so my fellow "` / `"country can do for"` at 2 s even though no meaningful Whisper boundary existed. Boundary matching itself works (clean sentence finals land with `boundary_found: true`).

**Decision (accepted):** the hard cap is a **bounded decision point**, not permission to manufacture an artificial caption boundary. The fallback rule is:

> If the stable prefix has no meaningful Whisper boundary when `BoundaryWaitBudget` expires, do **not** FINALize the interior stable prefix. Commit only the latest text backed by a **fully completed Whisper segment boundary**.

This preserves the two invariants:

- **I-1** — never discard uncommitted audio (the untouched tail stays in the buffer / partial).
- **I-2** — never deliberately turn an interior stable prefix into a FINAL.

#### Exact state behavior (2026-08-04, design only, no code)

Four rules replace the single `stable → commit` decision in `StreamingTranscriptCommitter.Update`:

```text
1. Stable + meaningful boundary                 → FINAL (commit the boundary)
2. Stable + no boundary, budget not expired     → keep waiting (pending, timer running)
3. Budget expires + still no boundary, but ≥ 1  → FINAL the LAST fully completed
   completed segment boundary exists within         segment boundary (commit the prefix
   the stable prefix                                up to it), keep the tail partial
4. Budget expires + no completed boundary        → keep partial; NEVER manufacture a
   exists yet                                        word-backed FINAL
```

Rule 4 is the critical anti-fragment case: when the whole stable prefix is inside a single still-open segment (e.g. stable = `"country can do for"` inside segment `"country can do for you"`), no segment boundary is completed, so nothing is committed — the fragment is never emitted. The eventual Whisper boundary (rule 1) determines the commit.

**Concrete mechanics on the current code:**

- Add `LastCompletedBoundaryLength(stable, segments)` → the **largest cumulative segment end `E` with `E <= stable.Length`** (the deepest real boundary the stable prefix has reached), mirroring the cumulative char-span scan already used by `EndsAtSegmentBoundary`/`AdvanceCommittedUntil`. Returns `0` when stable sits entirely inside the first (only partial) segment.
- In `Update`, the commit decision becomes:

```text
if pendingStable.Length > 0:
    if EndsAtSegmentBoundary(pendingStable, segments):        # rule 1
        newFinal = CommitStableText(pendingStable); ClearPending()
    elif BudgetExpired(now):                                   # rules 3/4
        E = LastCompletedBoundaryLength(pendingStable, segments)
        if E > 0:                                              # rule 3
            newFinal = CommitStableText(pendingStable[..E])
            pendingStable = pendingStable[E..]                 # tail stays the in-progress caption
            pendingStableSinceUtc = now                        # fresh decision point for the tail
        # else E == 0 → rule 4: keep partial, no FINAL
```

- Committing the `[0..E]` prefix keeps `CommitStableText`'s overlap/append semantics intact; `_currentEpochCommittedLength` advances to `E`, a real segment end, so `AdvanceCommittedUntil` backward-snaps correctly (I-1 preserved — no interior interpolation is ever introduced).
- The tail (`pendingStable[E..]`) is intentionally NOT cleared; it remains the live partial so the overlay keeps showing in-progress text, and its timer restarts so it gets its own full budget window rather than being re-fallback-committed instantly.

**Sizing note (unchanged, still provisional):** `BoundaryWaitBudget` stays 2 s. This change removes the *fragment* behavior of the cap; whether 2 s remains the right *latency* number is a separate re-derivation (Slice 6 baseline re-check) and is **not** touched here. Do not increase the budget as a substitute for this fix.

**Scope held:** `FindTailOverlap`, `CaptionService` dedup, overlay, wrapping, Argos, `StabilityWindow`, `DecodeInterval`, and the `CommittedUntilUtc` backward-snap are all **untouched** in this step. The duplicate-tail issue stays isolated until the premature-FINAL behavior is resolved.

**Evidence:** live trace file `artifacts/samples/adv7_trace_evidence.log` (gitignored) documents the pre-fix run: FINALs #1/#3/#4 = `boundary_found: false, fallback_used: true`; FINAL #2 = `boundary_found: true`.

## Non-goals

Explicitly out of scope so these are not chosen later as a "simpler fix":

- **Increasing `StabilityWindow` to 3/4/5.** It only delays the second-identical pass, pushing commits later without making them sentence-aware; it does not restore responsiveness we already earned and can regress first-FINAL latency. Rejected.
- **Adding concurrency or a worker pool to the commit path.** The commit path is serial and correct by design; concurrency addresses a different (translation) bottleneck and is rejected here.
- **Modifying the overlay / display layer.** Display is proven stable (FINAL-only). Untouched.
- **Adding arbitrary sentence-detection as a separate heuristic or model.** Boundary signals must come from the data we already record (segments), not a new detector.
- **Wrapping is a separate work item** and is not part of this ADR.

## Areas explicitly declared untouched

```text
Argos serialization     → not changed
Stop drain              → not changed
Wrapping                → separate
```

## Consequences

- Fragmented "bitin" captions (`At gusto ko`) should be replaced by captions that end at a meaningful boundary, while response remains bounded by the explicit latency cap.
- The `CommittedUntilUtc`/trim fix is a prerequisite; shipping boundary-aware commit without it risks amplifying the duplicate defect.
- New boundary machinery needs deterministic tests against the injected decoder seam, mirroring the existing STT fake-boundary harness.
- A latency measurement must accompany acceptance so we verify we did not regress the responsiveness baseline (Slice 6 / SAPI E2E).

## Alternatives Considered

- **Stabilize alone (bump `StabilityWindow`).** Simpler but pushes latency up without sentence-awareness; duplicate defect unaffected. Rejected.
- **Commit on boundary without the `stable` gate.** Almost- boundary-only would finalize mid-thought under Whisper noise/revision. Rejected; both-and required.
- **Wait indefinitely for a boundary (no hard cap).** Rejected explicitly — must never wait without bound.
- **Sentence-aware heuristic commit without `Trim`/`CommittedUntil` first.** Rejected as a prerequisite-violating order of work.
